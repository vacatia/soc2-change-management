# Changelog

Tracks changes to the process and the daily-scan prompt. The prompt itself carries no version stamp — git history + the date on each daily post are the source of truth; this log is the human-readable summary.

## 2026-08-06 — Classification lives on the record issue: label and decision comment together, project labels retired
Follows the 2026-08-05 review thread in #soc2-change-review. That thread settled *where* a decision comment lives (the issue, for consistency across Minor/Major/Emergency), and the discussion that followed extended the same logic to the label: if the decision comment is on the change's record issue, the label — a non-authoritative reflection of that decision — belongs there too. So both now sit on the **record issue**: the *SOC 2 Major Change* / *SOC 2 Emergency Change* parent issue, or a Minor's own issue. Discovery, saved views, and audit all key off issue labels; project-level classification labels are retired.
- **`scan-prompt.md` — decision comments go on the issue, never the project.** PR #7 had the scan read comments from both issues and projects; it now reads them from the record issue only — one consistent place to find a decision across Minor, Major, and Emergency changes.
- **`scan-prompt.md` — discovery moves from the project label to the issue label.** The primary query is now `issues(filter: {labels: {Major change issue label `10f23bd2…`}})` — each labelled *SOC 2 Major Change* parent issue is one Major change (whether a whole project or one of several inside a longer-running project); its `children` are the 8 checklist steps to health-check. Sibling issue labels `Minor change` (`936ea0c0…`) and `Emergency change` (`33423ab3…`) queried alongside. PREREAD §1 now lists one line per labelled parent issue, not per project.
- **`scan-prompt.md` — transitional dual discovery + migration surfacing.** Until the migration completes, the scan ALSO runs the old project-label query so no existing Major is missed, and surfaces any change still carrying a SOC 2 label on its *project* as a §4b item — "move the label to its parent/record issue." The whole clause retires once the project labels are archived.
- **`scan-prompt.md` — read-only label reconciliation.** The scan compares each record's issue label to its most recent decision comment and surfaces two kinds of drift in PREREAD §4b: stale-vs-decision ("label says X, latest decision Y → update to Y") and legacy-project-label (migration). Fix direction is always label→comment. The scan stays **read-only** — it surfaces, the owning team changes the label. Kept out of the LIGHT tripwire (low-urgency hygiene). §4 was broadened from "Retroactive classifications needed" to "Linear updates needed to match a decision" (4a retroactive calls, 4b label reconciliation).
- **`change-management-plan.md` — §2, §3, §4, §7, §10, appendix aligned.** §2: the change record is an issue, not a project. §3: labels apply to the record issue, project labels retired; the Emergency *project* template is retired in favor of a single *SOC 2 Emergency Change* parent-issue template (mirroring the Major change on 2026-08-03). §7: the Major outcome applies the label + writes the decision comment on the parent issue; the scan surfaces both stale and legacy-project labels. §10: "list of all changes" and "classification applied" evidence rows now key off issue labels and the decision comment.
- **In Linear (to do alongside this merge):** archive the three project-level labels (`Major`/`Minor`/`Emergency change`, ids `dd6bd0fb…`/`3251cf57…`/`6b958bab…`) once existing changes are relabelled onto their record issues; update the three issue-label descriptions to reflect that each is now the primary classification on a record issue (not just the "discrete major within a project" case); retire the *SOC 2 Emergency Change (Project)* template; and add a saved view filtered on the `SOC 2 Change Management` issue labels for the human at-a-glance list. Until then, dual discovery keeps the scan complete.

## 2026-08-05 — Decisions, not labels, are authoritative; PREREAD becomes a numbered agenda
From the 2026-08-05 SOC 2 Change Management Review. Two problems drove this: a label tells you nothing about *who* applied it or *why*, and the pre-read's bullets made items impossible to reference out loud in the meeting.
- **`scan-prompt.md` — no label is authoritative.** Previously the project-level `Major change` / `Minor change` / `Emergency change` labels were treated as on par with a review-group decision, and the project-label query was called the AUTHORITATIVE source. Nothing stops someone unfamiliar with this process from applying those labels, so they are now a strong signal only. The project query is demoted to "the primary discovery query" — still how designated Majors are found, no longer what makes the designation true.
- **`scan-prompt.md` — decision comments become the authoritative record.** State logic now checks Linear comments first, on both issues and projects. A decision comment opens with the marker line `**SOC 2 change review — {YYYY-MM-DD}**` and records the call plus the reasoning; the most recent one wins, so a reversal is just a later comment. Meeting notes in #soc2-change-review remain the fallback where no comment exists. The scan stays read-only — it reads these comments, it does not write them. Who writes them, and how they get reviewed, is still an open proposal.
- **`scan-prompt.md` — PREREAD is numbered throughout.** Sections are numbered 1–7 and items are numbered within each section, restarting at 1, so the meeting can say "section 4, item 2" instead of counting bullets. Bullets are banned from PREREAD output.
- **`scan-prompt.md` — bold was rendering as italic.** The prompt specified `*single-asterisk*` bold. Messages posted through the Slack API take standard Markdown, so every scan header since launch has posted in italic. Now specifies `**`.
- **`scan-prompt.md` — stale process questions.** The Open process questions section had no exit path: nothing could ever mark a question resolved, so questions aged indefinitely even after being settled in another channel. The section is now capped at 3, carried questions are phrased as a check rather than an accusation, and an explicit RETIRED list kills specific questions permanently. Seeded with Robert Lucido's Linear-comment/@-mention proposal, addressed outside this channel.
- **`scan-prompt.md` — dropped the `SOC2-minor` reference.** That label, plus `SOC2-major` and `SOC2-emergency`, were archived in Linear on 2026-08-05; they were an older DevOps-team set that predated this process and overlapped confusingly with the `SOC 2 Change Management` group. `SOC2-minor` had been on 80 DevOps issues, none of which change classification — no label already means Minor.
- **In Linear (2026-08-05):** an issue-level `Major change` label was created in the `SOC 2 Change Management` group, so a single Major change inside a long-running project can be labelled at the issue level and associated with that project's checklist, rather than requiring the whole project to be designated Major.
- **`change-management-plan.md` — Authorization clarified, and separated from the classification decision.** §4 step 3 now states what the business approver is actually confirming: that the change is needed and that what is being built is the right answer to that need — a business and product validation, not a compliance sign-off. §7 no longer treats the Authorization sub-issue as the home of the classification rationale; it cannot be, since Authorization only exists downstream of the group already deciding a change is Major. That leaves the classification decision and its reasoning living only in the meeting notes, which is the gap the decision-comment proposal above would close.
- **`change-management-plan.md` aligned.** §3 now lists `Major change` among the issue labels and explains when it applies: a long-running project that is not itself one major change but contains a discrete major change within it — possibly several over its life. §7 adds the matching path to the Major outcome — label the issue rather than the project, and associate it with the *SOC 2 Major Change* parent issue covering that change.

## 2026-08-03 — Major-change checklist becomes one parent issue with 8 sub-issues
Adopted by the review group at the 2026-07-29 SOC 2 Change Management Review. Previously the *SOC 2 Major Change* **project** template created the 8 checklist steps as 8 loose issues in the project, where they sat undifferentiated among the team's development issues and nothing pulled them together. They are now the sub-issues of a single *SOC 2 Major Change* parent issue, created from an **issue** template.
- **`change-management-plan.md`:** §3 reorganized around issue templates (Major + Emergency-issue) with the Emergency project template listed separately; notes that an issue template can be applied at any time, so a project reclassified Major follows the same path as one that starts out Major — the Linear-API workaround for reclassified projects is gone. §4 states the parent/sub-issue structure and standardizes the step titles to title case as used in Linear. §7 spells out the Major follow-through (label the project → apply the issue template → complete the steps → record in the Authorization sub-issue). §10 and the appendix updated.
- **`scan-prompt.md`:** the 8-step health check now reads the sub-issues of the parent checklist issue rather than loose issues in the project. Identifies the parent by its sub-issues being the 8 gates, not by title (older ones vary, e.g. "SOC2 Compliance"). A `Major change` project with no such parent issue is reported as having no checklist; projects that predate the template and still hold the 8 steps as loose issues are accepted, with a note. The project query now fetches `parent` on each issue.
- No change to labels: the project-level `Major change` label remains the authoritative designation and the unit that gets counted.
- **In Linear (2026-08-03):** the *SOC 2 Major Change* issue template was created at workspace level (parent issue + 8 sub-issues), and the *SOC 2 Major Change* project template was deleted so the old shape can no longer be created. The workspace now holds one project template (*SOC 2 Emergency Change (Project)*) and two issue templates (*SOC 2 Major Change*, *SOC 2 Emergency Change (Issue)*).

## 2026-07-24 — Two-tier scan + weekly review meeting
Introduces a standing weekly SOC 2 Change Management Review (Wednesdays) as the decision forum, and splits the scan into two tiers to feed it.
- **`scan-prompt.md`:** split the single daily scan into two modes.
  - *LIGHT* (Mon/Wed/Thu/Fri) — an exception-based tripwire that posts a one-line heartbeat on quiet days and alerts only on shipped-un-triaged items, undecided imminent ships, new high-confidence Majors, or break-glass events.
  - *PREREAD* (Tue) — the comprehensive weekly digest and agenda for the Wednesday review, with a lean top-level post (TL;DR + big picture) and the detail in-thread. Adds §5 coverage-vs-target and §6 open-process-questions.
  - Added a bounded recently-shipped (Done) lookback to power the un-triaged check. Absence of a label alone never triggers it — no label still means Minor by default; it fires only when a shipped item was a prior open candidate or plausibly warranted a Major review.
  - State logic now treats the posted weekly meeting notes and the EM/engineer Linear update as the authoritative "resolved" signal.
- **`change-management-plan.md`:** §6 rewritten as the two-tier scan; §7 rewritten around the weekly review meeting and the notes-to-channel + Linear-by-EM decision-recording loop; §8 and the appendix updated.
- **`README.md`:** updated the "how the review works" section for the two-tier cadence and the weekly meeting.

## 2026-06-29 — Initial release
Establishes this repo as the canonical home for the change-management process and the daily review prompt.
- **`scan-prompt.md`:** read-only, state-aware daily scan. Posts a TL;DR plus three sections — big-picture status, in-process major changes with an 8-step health check, and candidates awaiting decision (with queue age). Forward-looking (excludes Done/Canceled). Written for a non-expert, cross-team audience. No targets in the output; the agent reports facts only. No @-mentions (humans pull people in).
- **`change-management-plan.md`:** migrated and reorganized from the v16 Google Doc, incorporating the emergency-change issue template, the `Minor change` labels, the permanent multi-window framing, and the AI operating model.
